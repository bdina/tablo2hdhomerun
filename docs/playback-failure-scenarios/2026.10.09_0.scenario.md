This document captures detailed timelines, cross-component accounting, and root-cause analyses for live TV streaming failures observed during playback. These empirical incident reports serve as architectural reference cases to drive resiliency, stream stability, and watchdog design improvements in `tablo2hdhomerun`.

## 2. Executive Summary of Incident

A manual test was performed to stream a live TV channel from a Tablo 4th Gen tuner through the `tablo2hdhomerun` proxy, into Plex Media Server, and down to an iPad client. 

**The failure sequence was as follows:**
1. **Initial iPad Stream (Failed)**: The user attempted to start a Live TV session from the Plex iPad app. The app sat for a few moments and then went to a black screen, failing to play video. The user then exited the stream.
2. **Web Client Stream (Succeeded)**: The user opened the Plex Web client and initiated the same Live TV channel. The video started playing successfully without issue.
3. **Second iPad Stream (Succeeded)**: The user reopened the iPad client and initiated the channel. Video started playing successfully.

**Conclusion:** 
This behavior is driven by a transient transcode-initialization quirk in Plex's Live TV transcoder, not a defect or disconnect within `tablo2hdhomerun`. Because the iPad client forces transcoding (iOS does not support native MPEG-TS/MPEG2), Plex spins up an FFmpeg process. When the first HLS segments from the proxy do not start exactly on a clean keyframe (I-Frame) or sequence header, FFmpeg errors out with `Invalid frame dimensions 0x0`, causing the stream to halt and display a black screen. When the web client and subsequent iPad client connected, the `tablo2hdhomerun` proxy was already actively holding the stream open (via the idle-grace window) and buffering valid data, allowing the Plex transcoder to acquire clean keyframes immediately.

## 4. Root Cause Technical Deep Dive

### The "Black Screen" Transcoder Stall
When `tablo2hdhomerun` connects to the Tablo and requests the channel playlist, it downloads the first `.ts` segments and pushes them directly down the HTTP pipe to Plex.

Unlike file-based playback where the first byte is guaranteed to be a sequence header, Live TV HLS segments are a rolling window. Even though HLS segments theoretically cut on IDR frame boundaries, the first payload delivered to FFmpeg might drop the transcoder midway through a Group of Pictures (GOP) or lack a fully formed Program Association Table (PAT) and Program Map Table (PMT) precisely at the head of the stream. 

When the iPad forced Plex to transcode the stream:
1. Plex spun up the FFmpeg `Transcode runner`.
2. FFmpeg ingested the MPEG-TS bytes but failed to find a valid picture start code or sequence header within its probe timeout window.
3. FFmpeg threw `[mpeg2video @ ...] Invalid frame dimensions 0x0.`
4. Because FFmpeg was stuck waiting for dimensional data to initialize the VAAPI hardware encoder or software scaler, no output fragments were generated for the iPad client.
5. The iPad client player sat on a black screen waiting for DASH chunks that would never arrive.

### Why the Web Client and Second iPad Attempt Succeeded
The proxy's `idle-grace` feature (a 75-second hold) prevented the Tablo tuner from releasing the channel when the iPad disconnected. 

When the Web Client connected 30 seconds later, `tablo2hdhomerun` performed a **fast-attach**. The stream was already fully established, and `tablo2hdhomerun` was continuously reading from the rolling HLS playlist. Because the stream was already flowing with proper continuity, the next segment fed to Plex contained fully formed PAT/PMT/IDR frames, allowing Plex's transcoder/demuxer to easily acquire picture synchronization and start playback immediately.

The exact same mechanic allowed the second iPad attempt to succeed.

## 5. Architecture & Design Decisions

This scenario validates several aspects of the proxy's design while highlighting an inherent challenge of bridging HTTP-Live-Streaming into a raw MPEG-TS pipeline.

### 1. `idle-grace` Feature Validation
This incident proves the immense value of the `idle-grace` window in `tablo2hdhomerun`. Without it, the iPad's disconnect would have instantly torn down the Tablo tuner. The subsequent connection from the Web Client would have required a cold tune (10–12 seconds), heavily frustrating the user. Instead, the Web Client fast-attached instantly.

### 2. Upstream TS Parsing (Future Consideration)
While the `tablo2hdhomerun` logs are clean, the proxy currently acts as a "dumb pipe", concatenating `.ts` files and forwarding them to Plex.

**Future Consideration:** 
If these cold-start transcode failures become frequent, `tablo2hdhomerun` could be modified to execute a "clean start" algorithm. When a cold tune occurs, the proxy could parse the incoming MPEG-TS packets, dropping all video packets (`PID 0xXXXX`) until it detects a `PAT`, `PMT`, and an MPEG-2 Sequence Header (`0x000001B3`) / H.264 IDR frame. It would then start forwarding data to Plex exactly at that boundary.

**Current Decision:**
For now, this will be classified as a transient Plex Transcoder quirk. The complexity of writing an MPEG-TS demuxer into the proxy to find I-frames outweighs the current frequency of the bug, given that restarting the stream usually resolves it immediately via the fast-attach mechanism.
