This document captures detailed timelines, cross-component accounting, and root-cause analyses for live TV streaming failures observed during playback. ## 2. Executive Summary of Incidents

Between `2026-10-08 01:25 UTC` and `03:08 UTC`, two playback sessions streaming CBS Channel 4.1 failed after experiencing severe video stuttering, macroblock corruption, and repetitive audio/video dropouts:

1. **Session 1 (`01:25:48` – `02:27:56 UTC`)**: Streamed for 62 minutes under a continuous retune loop (**168 cold retunes**, averaging one every ~22 seconds) resulting in **>2,300 decoder error events** in Plex before the client disconnected.
2. **Session 2 (`02:57:29` – `03:07:22 UTC`)**: Streamed for 9.8 minutes under the identical retune loop (**26 cold retunes**, averaging one every ~22 seconds) generating **>5,960 decoder error events** in Plex before client disconnection.

### Primary Root Cause
The newly introduced `StallWatchdog` in `ResilientHlsSource.scala` was configured with a default micro-stall threshold:
- `microStallGap = 1.second`
- `microStallWindow = 60.seconds`
- `maxMicroStalls = 5`

In live HLS streaming, the Tablo writes and publishes discrete MPEG-TS segments with durations between 2.0 and 3.0 seconds. The proxy downloads and emits a segment over ~50–200 ms, followed by a natural inter-segment arrival gap of ~2.0–2.9 seconds while waiting for the next segment to be encoded.

Because every regular segment boundary exceeded the 1.0-second gap threshold (`gap > 1.second`), the watchdog misdiagnosed healthy, normal HLS segment delivery as a series of "micro-stalls". After receiving 6 consecutive segments (~18 seconds into playback), the watchdog declared `too many micro-stalls (> 5 in 60s), retuning` and failed the stream stage. This forced `RestartSource` into a cold `/watch` retune cycle every ~18–22 seconds, triggering a destructive storm of stream discontinuities and decoder crashes.

## 6. Root Cause Technical Deep Dive

### 6.1 Flawed Watchdog Pacing on Live Segmented Streams

The logic responsible for the failure loop is located in [`src/main/scala/app/stream/ResilientHlsSource.scala`](file:///home/bdina/git/tablo2hdhomerun/src/main/scala/app/stream/ResilientHlsSource.scala#L107-L137):

```scala
override def onPush(): Unit = {
  val now = System.nanoTime()
  var shouldFail = false
  if (started) {
    val gap = now - lastPushNanos
    if (gap > microStallGapNanos) {
      val cutoff = now - microStallWindowNanos
      microStallTimestamps = (now :: microStallTimestamps).filter(_ >= cutoff)
      if (microStallTimestamps.size > maxMicroStalls) {
        shouldFail = true
        log.warn(s"[$streamName] too many micro-stalls (> $maxMicroStalls in ${microStallWindow.toSeconds}s), retuning")
        failStage(new StallTimeoutException(s"$streamName too many micro-stalls"))
      }
    }
  }
  if (!shouldFail) {
    started = true
    lastPushNanos = now
    scheduleOnce("watchdog", stallTimeout)
    push(out, grab(in))
  }
}
```

#### Why This Failed for HLS
1. In an MPEG-TS byte stream fed from an HTTP HLS poller, data is pushed in discrete chunk bursts corresponding to downloaded `.ts` segments (e.g. 2–3 MB bursts every 2–3 seconds).
2. Because `microStallGap` was set to `1.second`, the time elapsed between the final chunk of segment $N$ and the initial chunk of segment $N+1$ was routinely `1,800 ms – 3,100 ms`.
3. Consequently, **every normal segment transition was counted as a micro-stall**:
   ```text
   2026-10-08 03:06:55.370 INFO [4thgen-channel-S20431_004_01] real data resumed after 1683ms  --> stall count 1
   2026-10-08 03:06:58.457 INFO [4thgen-channel-S20431_004_01] real data resumed after 2822ms  --> stall count 2
   2026-10-08 03:07:01.546 INFO [4thgen-channel-S20431_004_01] real data resumed after 2823ms  --> stall count 3
   2026-10-08 03:07:04.634 INFO [4thgen-channel-S20431_004_01] real data resumed after 2880ms  --> stall count 4
   2026-10-08 03:07:07.726 INFO [4thgen-channel-S20431_004_01] real data resumed after 2794ms  --> stall count 5
   2026-10-08 03:07:10.815 WARN [4thgen-channel-S20431_004_01] too many micro-stalls (> 5 in 60s), retuning
   ```
4. Exactly every 5 to 6 segments (~18 to 22 seconds), the watchdog aborted the stage.

### 6.2 Cascading Failure Through Plex's Transcode Pipeline
When `failStage` was called, `RestartSource` executed a cold retune:
1. `ResilientHlsSource` injected `MPEGTS_DISCONTINUITY_PACKET` followed by `cachedHeaders.syncPrefix` (PAT/PMT).
2. Plex's `mpeg2video` decoder received a discontinuity packet while in the middle of decoding a GOP (Group of Pictures).
3. P-frames and B-frames referencing missing past/future reference frames failed immediately with:
   - `00 motion_type at X Y` (missing motion vector)
   - `ac-tex damaged` (corrupted DCT coefficients)
   - `Missing picture start code` (out-of-sequence PES/TS headers)
   - `Invalid mb type in B-frame`
4. Repeating this every 20 seconds saturated the decoder with corrupt frames, leading to visual freezing and client playback failure.

### 6.3 Grace Period Termination Mechanics
Neither session crashed the `tablo2hdhomerun` daemon. Instead:
1. The client player (Chrome) hit unrecoverable playback stalls and was closed or navigated away by the user.
2. Plex Media Server noticed the client pipe was closed and logged `WARN - Failed to find consumer`.
3. PMS immediately severed its HTTP connection to `http://192.168.2.24:8080/auto/v4.1`.
4. `tablo2hdhomerun` detected that `clients` dropped to `0` and engaged its **75-second idle grace timer**.
5. When no client reconnected within 75 seconds, `[session] grace-expired` triggered, cleanly tearing down the tuner session and releasing Tablo resources.

## 7. Architecture & Design Recommendations

To prevent healthy streams from entering self-induced retune storms and to improve overall stream resilience, the following design changes are recommended:

### 1. Remove or Decouple Chunk-Level Micro-Stall Detection from HLS Streams
- **Segment-Aware Cadence**: In HLS mode, stall detection must be based on **segment availability from the playlist**, not raw byte-push timestamps. A stream is healthy as long as new segments are added to `pl.m3u8` within the playlist's `#EXT-X-TARGETDURATION` plus a reasonable margin (e.g. `targetDuration * 1.5 + 2s`).
- **Eliminate `microStallGap` on Byte Pushes**: An inter-push gap of 1.0 second is completely normal when reading HTTP segment chunks. If micro-stall detection is retained, `microStallGap` must either:
  - Be raised significantly above the maximum HLS segment duration (e.g. `> 6.seconds`), OR
  - Only apply to continuous CBR streams (such as direct tuner TS sockets), not segmented HLS.

### 2. Differentiate RF Dropouts from Normal HLS Ingestion
- In HLS streaming, the Tablo creates segments of 2–3 seconds. During a genuine RF signal drop, the Tablo either stops publishing new segment URLs to the playlist or publishes truncated segments.
- `HlsPlaylistPoller` already tracks sequence numbers and target duration. The primary signal for stream stalling should come from the **poller failing to discover new sequence IDs within `stallTimeoutSec` (8s)**, rather than `ResilientHlsSource`'s internal chunk timer.

### 3. Implement Exponential Backoff or Retune Throttling
- During an outage or repeated failure condition, cold retuning every 20 seconds over 160+ iterations overwhelms both the Tablo hardware and the downstream decoder.
- Implement retune circuit-breaking / rate limiting: if $\ge 3$ retunes occur within 60 seconds without sustained playback of at least 30 seconds, back off retune attempts (e.g. 5s, 10s, 20s) to give upstream tuners and RF demodulators time to settle.

### 4. Downstream Discontinuity Rate-Limiting
- Downstream transcoders (Plex/FFmpeg) cannot tolerate high-frequency timeline discontinuities. If retunes occur closer together than a single GOP cycle (~1–2 seconds of video), the stream should continue padding with MPEG-TS null packets until a coherent keyframe/GOP is acquired before injecting the discontinuity and PAT/PMT headers.
