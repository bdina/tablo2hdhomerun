## 2. Executive Summary of Incident

On `2026-10-08`, an extended live TV playback session streaming CBS Channel 4.1 ran for **97 minutes 46 seconds** (`11:27:31 UTC` – `13:05:17 UTC` / `07:27:31 EDT` – `09:05:17 EDT`) before terminating after catastrophic stream degradation and client abandonment.

- **Session Duration**: 97.7 minutes (1 hour 37 minutes 46 seconds)
- **Tuning Operations**: **274 cold tuning cycles** (1 initial tune + **273 recovery retunes**)
- **Retune Cadence**: Average interval of **21.44 seconds** (min 15.92s, max 35.26s)
- **Watchdog Trip Breakdown**: **100% (273/273)** of recovery retunes were triggered by `StallWatchdog` declaring `too many micro-stalls (> 5 in 60s), retuning`
- **Plex Decoder Errors**: Over **330 decoder error and warning events** recorded in Plex Media Server logs, including repeated macroblock corruption, motion vector unavailability, slice mismatches, and terminal `Error submitting packet to decoder: Invalid data found when processing input`
- **Client Impact**: Video playback suffered from periodic freezes, macroblocking artifacts, and buffer underruns every ~21 seconds, until the client player permanently halted and Plex reported `Failed to find consumer`

### Primary Root Cause
The `StallWatchdog` stage in [`ResilientHlsSource.scala`](file:///home/bdina/git/tablo2hdhomerun/src/main/scala/app/stream/ResilientHlsSource.scala#L84-L137) misinterprets normal live HLS segment pacing as a series of stream "micro-stalls". 

In live HLS transmission, the Tablo hardware packages OTA video into discrete MPEG-TS segments with durations of ~2.0–3.0 seconds. The proxy downloads and pushes each segment over ~50–200 ms, followed by a natural inter-segment arrival gap of ~1.8–3.1 seconds while awaiting the next segment from the Tablo encoder.

Because `StallWatchdog` was configured with `microStallGap = 1.second` and `maxMicroStalls = 5` within a 60-second window, **every single regular segment boundary was categorized as a micro-stall violation**. After receiving 6 consecutive segments (~18–22 seconds), the watchdog unconditionally tripped, failing the stream with [`StallTimeoutException`](file:///home/bdina/git/tablo2hdhomerun/src/main/scala/app/stream/ResilientHlsSource.scala#L127). This forced the proxy into an endless loop of cold `/watch` retunes, injecting MPEG-TS discontinuity packets and cached PAT/PMT prefixes into the downstream transcoder every ~21 seconds.

## 5. Root Cause Technical Deep Dive

### 5.1 Flawed Watchdog Pacing on Live Segmented Streams

The logic responsible for the failure loop is located in [`src/main/scala/app/stream/ResilientHlsSource.scala`](file:///home/bdina/git/tablo2hdhomerun/src/main/scala/app/stream/ResilientHlsSource.scala#L116-L137) ([commit 9a4e105](file:///home/bdina/git/tablo2hdhomerun/src/main/scala/app/stream/ResilientHlsSource.scala)):

```scala
override def onPush(): Unit = {
  val now = System.nanoTime()
  var shouldFail = false
  if (started) {
    val gap = now - lastPushNanos
    if (gap > microStallGapNanos) {
      val cutoff = now - microStallWindowNanos
      microStallTimestamps = (now :: microStallTimestamps).filter(_ >= cutoff)
      if (microStallTimestamps.size > maxMicroStalls) {
        shouldFail = true
        log.warn(s"[$streamName] too many micro-stalls (> $maxMicroStalls in ${microStallWindow.toSeconds}s), retuning")
        failStage(new StallTimeoutException(s"$streamName too many micro-stalls"))
      }
    }
  }
  if (!shouldFail) {
    started = true
    lastPushNanos = now
    scheduleOnce("watchdog", stallTimeout)
    push(out, grab(in))
  }
}
```

#### Why This Failed for HLS
1. In an MPEG-TS byte stream fed from an HTTP HLS poller, data is pushed in discrete chunk bursts corresponding to downloaded `.ts` segments (e.g. 2–3 MB bursts every 2–3 seconds).
2. Because `microStallGap` was configured to `1.second`, the time elapsed between the final chunk of segment $N$ and the initial chunk of segment $N+1$ was routinely `1,800 ms – 3,100 ms`.
3. Consequently, **every normal segment transition was counted as a micro-stall**:
   ```text
   2026-10-08 11:27:40.178 INFO [4thgen-channel-S20431_004_01] real data resumed after 1955ms  --> stall count 1
   2026-10-08 11:27:42.238 INFO [4thgen-channel-S20431_004_01] real data resumed after 1863ms  --> stall count 2
   2026-10-08 11:27:44.295 INFO [4thgen-channel-S20431_004_01] real data resumed after 1804ms  --> stall count 3
   2026-10-08 11:27:47.385 INFO [4thgen-channel-S20431_004_01] real data resumed after 2927ms  --> stall count 4
   2026-10-08 11:27:50.480 INFO [4thgen-channel-S20431_004_01] real data resumed after 1957ms  --> stall count 5
   2026-10-08 11:27:53.570 WARN [4thgen-channel-S20431_004_01] too many micro-stalls (> 5 in 60s), retuning
   ```
4. Exactly every 5 to 6 segments (~18 to 22 seconds), the watchdog aborted the stage.

### 5.2 Cascading Failure Through Plex's Transcode Pipeline
When `failStage` was called, `RestartSource` executed a cold retune:
1. `ResilientHlsSource` injected `MPEGTS_DISCONTINUITY_PACKET` followed by `cachedHeaders.syncPrefix` (PAT/PMT).
2. Plex's `mpeg2video` decoder received a discontinuity packet while in the middle of decoding a GOP (Group of Pictures).
3. P-frames and B-frames referencing missing past/future reference frames failed immediately with:
   - `00 motion_type` (missing motion vector)
   - `ac-tex damaged` (corrupted DCT coefficients)
   - `Missing picture start code` (out-of-sequence PES/TS headers)
   - `Invalid mb type in P-frame` / `B-frame`
4. Repeating this every ~21 seconds for over 96 minutes saturated the decoder with corrupt frames. By minute 88–94, FFmpeg's packet demuxer hit unrecoverable framing corruption, throwing `Error submitting packet to decoder: Invalid data found when processing input`.

### 5.3 Hardware Endurance vs Stream Stability
- The Tablo 4th Gen hardware handled **274 consecutive `/watch` POST requests** and **273 session terminations** without a hardware lockup or crash.
- This demonstrates that the Tablo hardware and its HTTP server are robust, but the proxy's self-inflicted retunes repeatedly severed GOP delivery, preventing the client from ever establishing a smooth stream.

### 5.4 Grace Period Termination Mechanics
Neither session crashed the `tablo2hdhomerun` daemon:
1. The client player (Chrome) hit unrecoverable playback stalls and closed at `13:04:02.669 UTC` (`09:04:02.669 EDT`).
2. Plex Media Server logged `WARN - [Req#6bd85/Live/...] Failed to find consumer` and closed the HTTP connection to `/auto/v4.1`.
3. `tablo2hdhomerun` detected that `clients` dropped to `0` at `13:04:02.604 UTC` and engaged its **75-second idle grace timer**.
4. During the grace period, retune attempt 274 executed at `13:05:05.084 UTC`.
5. At `13:05:17.604 UTC` (exactly 75.000 seconds after disconnect), `[session] grace-expired` triggered, cleanly tearing down lease `552a0ffa` and releasing all Tablo tuner resources.

## 6. Architecture & Design Recommendations

Based on the evidence from this 97-minute incident and prior sessions, the following architectural fixes are recommended for `tablo2hdhomerun`:

### 1. Remove or Decouple Chunk-Level Micro-Stall Detection from HLS Streams
- **Segment-Aware Cadence**: In HLS mode, stall detection must be based on **segment availability from the playlist**, not raw byte-push timestamps. A stream is healthy as long as new segments are added to `pl.m3u8` within `#EXT-X-TARGETDURATION` plus a reasonable margin (e.g. `targetDuration * 1.5 + 2s`).
- **Eliminate `microStallGap` on Byte Pushes**: An inter-push gap of 1.0 second is completely normal when reading HTTP segment chunks. If micro-stall detection is retained, `microStallGap` must either:
  - Be raised significantly above the maximum HLS segment duration (e.g. `> 6.seconds`), OR
  - Only apply to continuous CBR streams (such as direct tuner TS sockets), not segmented HLS.

### 2. Differentiate RF Dropouts from Normal HLS Ingestion
- In HLS streaming, the Tablo creates segments of 2–3 seconds. During a genuine RF signal drop, the Tablo either stops publishing new segment URLs to the playlist or publishes truncated segments.
- `HlsPlaylistPoller` already tracks sequence numbers and target duration. The primary signal for stream stalling should come from the **poller failing to discover new sequence IDs within `stallTimeoutSec` (8s)**, rather than `ResilientHlsSource`'s internal chunk timer.

### 3. Implement Retune Circuit-Breaking & Exponential Backoff
- Under an outage or repeated failure condition, cold retuning every 20 seconds over 270+ iterations overwhelms both the Tablo hardware and the downstream decoder.
- Implement retune circuit-breaking / rate limiting: if $\ge 3$ retunes occur within 60 seconds without sustained playback of at least 30 seconds, back off retune attempts (e.g. 5s, 10s, 20s) to give upstream tuners and RF demodulators time to settle.

### 4. Downstream Discontinuity Rate-Limiting & GOP Alignment
- Downstream transcoders (Plex/FFmpeg) cannot tolerate high-frequency timeline discontinuities. If retunes occur closer together than a single GOP cycle (~1–2 seconds of video), the stream should continue padding with MPEG-TS null packets until a coherent keyframe/GOP is acquired before injecting the discontinuity and PAT/PMT headers.
